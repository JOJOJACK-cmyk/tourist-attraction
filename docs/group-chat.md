# 그룹 채팅방

`/chat`에서 로그인하고 **새 채팅방 만들기**에 방 이름과 별명을 입력합니다. 방장은 **초대 링크 복사**로 친구를 초대합니다. 초대받은 사람도 로그인한 뒤 방 안에서 사용할 별명으로 참여합니다. 일반 회원가입·로그인을 채팅 화면에서 할 수 있습니다. 소셜 로그인 설정은 기존 기능으로 유지하며 여기서는 일반 로그인을 바로 제공합니다.

## 구현 범위

- 참여한 방만 목록에 표시하고 그룹별 대화 기록을 MySQL에 저장합니다. 초기 가짜 방/대화는 넣지 않습니다.
- 방마다 계정과 별명을 구분하며 실제 아이디·소셜 제공자 ID는 다른 참여자에게 표시하지 않습니다. 별명은 방 안에서 중복되지 않아야 합니다.
- 방장은 참여자를 내보내거나 방을 닫을 수 있습니다. 내보낸 계정은 같은 초대 링크로 재참여할 수 없습니다.
- 일반 참여자는 나갔다가 초대 링크로 다시 들어갈 수 있습니다. 방장은 먼저 방을 닫은 후 나갑니다.
- 닫힌 방은 새 참여·송신이 차단되지만 남아 있는 참여자는 기록을 볼 수 있습니다. 나간 계정은 기록을 볼 수 없습니다.
- 방별 최대 50명, 방 이름 2~60자, 별명 2~16자, 메시지 1~1,000자입니다.
- 메시지는 Enter로 전송하고 Shift+Enter로 줄바꿈합니다. 한글 조합 중 Enter는 전송하지 않습니다.
- 최신 50개와 ID 기반 이전 대화를 조회합니다. 실시간 메시지와 기록 조회가 겹치면 ID로 중복을 제거합니다.
- 연결 종료 시 최대 5회 자동 재연결합니다. 연결되지 않은 동안 전송은 비활성화합니다. 초대 링크 복사가 지원되지 않는 환경은 선택 가능한 텍스트를 보여줍니다.

## 데이터

| 테이블 | 내용 |
| --- | --- |
| chat_room | 방 이름, 방장, 임의 초대 토큰, 닫힘 상태, 생성 시각 |
| chat_membership | 방·회원 관계, 방 안 별명, 참여/퇴장/차단 상태 |
| chat_message | 방, 발신 참여 관계, 발신 시 별명, 내용, 시각 |

`ddl-auto=update`로 기존 DB에 새 테이블을 추가합니다. 기존 회원·게시글은 이 작업으로 삭제하지 않습니다. 초대 토큰은 SecureRandom 32바이트를 64자리 hex로 저장하며, 링크는 방장에게만 제공합니다. 링크를 받은 로그인 사용자는 이름과 인원을 미리 볼 수 있고, 참여해야 대화를 읽을 수 있습니다.

## API와 실시간 연결

| 요청 | 동작 |
| --- | --- |
| GET /api/chat/rooms | 참여한 방 목록 |
| POST /api/chat/rooms | name, alias로 방 만들기 |
| GET /api/chat/invites/{token} | 초대 확인 |
| POST /api/chat/invites/{token}/join | alias로 참여 |
| GET /api/chat/rooms/{id} | 방·참여자·방장 관리 정보 |
| GET /api/chat/rooms/{id}/messages?before={id} | 최신/이전 대화 50개 |
| POST /api/chat/rooms/{id}/messages | body로 메시지 보내기 |
| DELETE /api/chat/rooms/{id}/membership | 방 나가기 |
| DELETE /api/chat/rooms/{id}/participants/{participant} | 방장의 참여자 내보내기 |
| POST /api/chat/rooms/{id}/close | 방 닫기 |
| WS /ws/chat?room={id} | 같은 방의 실시간 이벤트 수신 |

모든 API와 WebSocket은 로그인 및 참여 권한을 검사합니다. REST 쓰기에 기존 세션 CSRF 토큰을 사용합니다. WebSocket은 Spring의 같은 출처 기본 검사를 유지하고, 실제 HTTP 세션과 해당 방의 활성 참여 관계를 검증합니다. 20초 heartbeat 및 이벤트 전달 시에도 세션·참여 상태를 재확인합니다. 클라이언트가 보낸 방장 여부·회원 ID·발신자 별명은 신뢰하지 않습니다.

메시지 저장과 관리 작업은 방의 pessimistic write lock으로 순서를 조정합니다. 성공한 트랜잭션의 AFTER_COMMIT 이벤트만 연결된 같은 방에 전달합니다. 메시지는 CSRF가 적용되는 REST로 저장하고 WebSocket으로 배포하는 구조이며 STOMP/SockJS는 사용하지 않습니다. 소켓 송신에는 ConcurrentWebSocketSessionDecorator를 사용합니다. 클라이언트는 textContent로 방 이름·별명·내용을 표시합니다.

## 로컬 확인

1. Maven 프로젝트를 새로고침하고 앱을 재시작합니다. 새 의존성은 spring-boot-starter-websocket입니다.
2. 일반 창에서 회원 A로 로그인 → 방 만들기 → 초대 링크 복사.
3. 시크릿 창에서 링크 열기 → 회원 B로 로그인/가입 → 별명으로 참여.
4. 양쪽에서 메시지를 보내고 새로고침 후 기록도 확인합니다.
5. 방장 A로 B를 내보내기 → B의 연결·대화 접근·재참여 차단을 확인합니다.
6. 방 닫기 → 새 메시지와 새 참여가 차단되고 기존 기록은 남는지 확인합니다.

같은 브라우저의 탭들은 로그인 세션을 공유하므로 서로 다른 계정 테스트는 시크릿 창이나 다른 브라우저를 사용합니다. localhost 초대 링크는 같은 PC에서만 접속됩니다. 실제 친구와 사용하려면 접근 가능한 서버 주소가 필요합니다.

자동 검증은 HTTP API·권한·초대·퇴장·대화 페이지 조회와 실제 임베디드 서버의 두 로그인 세션 및 WebSocket 연결을 사용합니다. 서로 다른 방의 격리, 내보낸 참여자·외부 Origin 거부, 방 닫기, 로그아웃에 따른 소켓 종료도 검증합니다. JavaScript 검증은 `node src/test/js/chat.test.cjs`입니다. MySQL 실연결과 실제 브라우저 레이아웃은 사용자 환경에서 추가 확인해야 합니다.

## 배포 범위

현재 한 Spring Boot 인스턴스에서 소켓 연결을 관리하며 기록은 DB에 저장합니다. 다중 서버 간 이벤트 공유·Redis, 읽음 표시, 파일 전송, 모바일 푸시, 메시지 삭제·방 재개, 초대 토큰 교체는 포함하지 않습니다. 프록시는 WebSocket Upgrade와 적절한 타임아웃을 지원해야 하며 HTTPS 페이지에서는 자동으로 WSS를 사용합니다. 연결 버퍼에는 64KB 한도를 둡니다.

공식 구현 참고: https://docs.spring.io/spring-framework/reference/6.2/web/websocket/server.html
